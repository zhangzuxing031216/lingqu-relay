# 充值 / 支付（可选）

> 不接支付也能运营：后台手动加额度、发兑换码、内部记账。
> 接支付前，先把“用户、令牌、扣费”跑通。

## 1. 先想清楚

| 问题 | 说明 |
|---|---|
| 谁收款 | 个人/公司/平台 |
| 用什么支付 | 易支付/其他聚合支付/官方商户 |
| 回调地址 | 以 new-api 后台显示的 `notify_url` 为准 |
| 退款 | 谁处理、多久、什么条件 |
| 对账 | 每天/每周核对订单和到账 |
| 风控 | 大额、频繁、异常 IP |

## 2. 配置步骤（通用）

1. 在支付商后台创建应用，拿 `pid` / `key`（或商户号/密钥）。
2. 在 new-api 后台找到支付/充值设置。
3. 填：
   - 支付方式
   - `pid` / `key`
   - 回调/通知地址（用后台显示的，不要自己猜）
   - 同步跳转地址（支付完成返回页）
4. 保存。
5. 用小额（1 元）下单。
6. 支付完成后看：
   - 支付商订单状态
   - new-api 充值记录
   - 用户额度是否增加
7. 再测：
   - 取消支付
   - 重复回调
   - 回调延迟
   - 金额不一致
   - 签名错误

## 3. 回调安全

服务端必须：

- 校验签名。
- 校验金额与订单金额一致。
- 校验订单号存在且未处理。
- 幂等：同一订单重复回调只加一次。
- 记录原始回调（脱敏）用于对账。
- 失败返回支付商要求的格式，不要返回 HTML。

**不要**：

- 只信前端 `?status=success`。
- 把密钥写进前端 JS。
- 在回调里直接 `+额度` 不做幂等。
- 用测试密钥收真钱。

## 4. 对账

每天：

```text
支付商订单列表
  ↔ new-api 充值记录
  ↔ 用户额度变化
```

差异处理：

| 差异 | 处理 |
|---|---|
| 支付成功、系统没单 | 查回调地址/验签/日志，手动补单需审批 |
| 系统有单、支付没成功 | 不要发货，等回调 |
| 金额不一致 | 以支付商为准，人工核对 |
| 重复到账 | 修幂等，追回/记录 |

> 手动补单前先备份数据库，并记录操作人/原因/订单号。

## 5. 退款

- 制定明确规则：未使用可退、已消耗不退、手续费谁承担。
- 退款后同步扣回额度或封号。
- 保留聊天/订单证据。
- 大额退款人工审核。

## 6. 定价与手续费

```text
售价 = 上游成本 × (1 + 毛利) + 支付手续费 + 汇率损耗
```

- 毛利建议 ≥30%，覆盖失败请求/退款/汇率。
- 不要做“1 元无限量”。
- 不要承诺“永久有效”。
- 定期按上游调价。

## 7. 合规

- 支付业务需要相应资质/商户号，按当地法律。
- 不洗钱、不跑分、不代收。
- 不向未成年人/受限地区提供违规服务。
- 保存必要的交易记录，注意隐私。
- 有用户协议/隐私政策/退款政策。

## 8. 测试清单

```text
[ ] 1 元支付成功 → 到账
[ ] 取消支付 → 不到账
[ ] 重复回调 → 只到账一次
[ ] 签名错 → 拒绝
[ ] 金额改小/改大 → 拒绝
[ ] 订单号不存在 → 拒绝
[ ] 回调延迟 → 最终到账
[ ] 退款 → 额度扣回
[ ] 对账 → 无差异
```

## 9. 不接支付时的替代

- 兑换码：后台生成，手动发。
- 手动充值：管理员加额度，记录原因。
- 内部记账：Excel/数据库，定期对账。
- 邀请制：只给信任的人开号。

> 小站早期，手动充值反而更安全：没有回调伪造、没有支付密钥泄露。先把产品和用户跑通，再接支付。
